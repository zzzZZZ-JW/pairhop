# Chrome 重启与窗口重开漏触发排查

日期：2026-09-05。正式发布版本：0.1.2。用户已确认实测通过并授权直接发布。下列真实配对记录来自 0.1.2-dev；正式版只将版本标识改为 0.1.2，配对引擎代码不变。正式签名二进制哈希另列于发布校验文件。

## 两条失效路径

1. **完全退出 Chrome 后重启**：旧服务仍存活、权限正常、Chrome 监听注册返回成功，但用户打开配对界面后没有新的有效事件；Apple 帮助程序实际存在，服务却仍显示零个。界面工具访问 Chrome 后可以恢复，原有自动化测试因此掩盖了问题。
2. **仅关闭所有窗口，保留 Chrome 进程，再开窗口**：首轮补上初始化后，用户验证两次完全退出路径成功，但窗口重开仍失败。代码只在帮助程序缓存为空时重新发现来源，无法处理 Chrome 没退出而 native messaging 帮助程序已经更换的情况。

Chrome 152 的实现明确在读取应用的 `accessibilityRole` 时启用原生辅助功能接口。旧代码只创建 AX 对象和注册通知，没有读取应用角色。修复按每个已验证进程的生命周期初始化，激活时也重新确认可用性；没有设置全局 Chrome flags，也没有使用 `AXEnhancedUserInterface` 强制屏幕阅读器模式。

来源：[当前实测 Chrome 版本源码](https://chromium.googlesource.com/chromium/src/+/refs/tags/152.0.7977.76/chrome/browser/chrome_browser_application_mac.mm#480)、[Chromium 原生辅助功能初始化测试](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/chrome/browser/chrome_browser_application_mac_browsertest.mm)、[Apple AX 通知注册返回值](https://developer.apple.com/documentation/applicationservices/1462089-axobserveraddnotification)。

## 修复内容

- 每个新的签名已验证进程都先读取应用角色，再建立监听；Chrome 激活时重新确认接口可用。
- 发现官方六位输入表单时始终核对当前进程集合。使用 `NSRunningApplication` 身份和终止状态清理旧观察器，不能将缓存非空当成进程仍有效。
- 把暂时 IPC 失败、权限错误与“不支持此通知”分开。启动、激活和唤醒后的恢复最多持续约 3 秒，150 ms 间隔，只重试尚未注册的通知；后续真实生命周期事件可重新发起恢复。
- 唤醒后重建观察器；休眠/锁定期间停止恢复任务，保留已有请求的防重复输入记录。
- `status` 改为只读现有快照。`diagnose` 才主动刷新观察器并检查界面，避免查询行为掩盖触发缺陷。
- 状态新增已观察的进程编号、待注册数量和不含内容的 AX 错误码；验证码仍不写入文件或日志。

没有添加稳定空闲时的周期扫描。对普通网页仍只做原有的有限焦点祖先检查；只有官方配对表单触发帮助程序核对。

完整修复后的四次记录：就绪到输入完成 **116–130 ms**，发现请求到确认连接 **364–424 ms**。[不含验证码、UUID、进程编号和时间戳的验证数据](evidence/stability-validation.json)。

末轮验证由用户正常操作 Chrome；没有使用界面工具读取 Chrome，也没有调用 `diagnose` 修复监听，仅被动读取本工具的状态/结果文件。因此不依赖测试工具替助手初始化接口。

这是本机两条已复现路径的回归验证，不是数天持续运行或其他 macOS / Chrome 版本的兼容保证。睡眠唤醒等代码路径尚未重新进行真实设备测试；未重新测量 15 分钟功耗，旧性能数据不能移作本二进制的测量值。

## 测试期间的 Chrome 提示

排查时通过界面工具退出 Chrome 后，紧接着读取该应用，工具返回 `procNotFound (-600)`；用户同时看到“Google Chrome.app 已不能再打开”。随后 Chrome 正常启动并完成了配对。系统和用户诊断报告目录未找到该时段的 Chrome 崩溃记录。现有证据更符合测试中的退出/访问时序冲突，不能据此认定它是原先漏触发的诱因。之后停止了这类界面操作，改用用户正常操作验证。
